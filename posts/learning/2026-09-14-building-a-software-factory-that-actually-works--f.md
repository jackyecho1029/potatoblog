## 📋 Brief

这支视频讲的是怎么用 AI 代理搭建一个「软件工厂」——不是随便打几行提示词就完事，而是把开发流程拆成流水线，让多个 AI 同时干活还不互相踩脚。嘉宾 Ross Mike 拆解了他自己用的五六个小文件，看完你就能自己搭一套。

## 📖 详细内容

### 01｜软件工厂不是产品，是你的工作方式

**核心观点：** 现在有很多创业公司打着「软件工厂」的旗号卖产品，但 Ross 说得很直白：软件工厂跟用什么模型、什么工具都没关系。它是把一个人的工作流、技能和领域知识，打包成开发过程中的具体技能文件。核心就一句话：在开发的每个环节，怎么让模型发挥最大能力，同时跑得快还不掉质量。

**重要原话：**
> "A software factory is more about someone's workflow, skills, and domain knowledge, and it's packed up in specific skills that they use in their development process."
>
> （原文：软件工厂更多是关于某人的工作流、技能和领域知识，然后被打包成开发过程中使用的具体技能。）

**个人感受：** 我挺喜欢他把这个概念「去商品化」的做法。现在太多人想把流程包装成付费产品，其实说白了就是你自己的做事方法写成了文档。

**延伸思考：** 这跟当年 DevOps 的兴起很像——工具重要，但真正拉开差距的是你怎么组织流程。AI 时代也一样，模型大家都能用，差的是系统。

**可参考的行动：** 回想你上次用 Claude Code 或 Cursor 做项目的流程，拿张纸写下每一步你是怎么做的、哪里卡壳了。这是搭建你自己工厂的第一份草稿。

---

### 02｜第一步「隔离」：别让代理互相踩脚

**核心观点：** 大多数人用 AI 开发是线性的：一次做一个功能，做完再做下一个。想并行就出事——代理删文件、覆盖别人的代码。Ross 的解法是每个新功能都在从主分支切出来的全新 Git worktree 里开工，代理各自在「副本」上工作，做完再合并回去，永远不会冲突。

**重要原话：**
> "Every new feature starts in a fresh Git work tree branched from origin main, so agents can work in parallel without conflicts. Never build on main."
>
> （原文：每个新功能都从 origin main 切出的全新 Git worktree 开始，代理可以并行工作互不冲突。永远不要在 main 上开发。）

**个人感受：** 「Agent deleted my files」这种吐槽我在网上见过太多次了，原来几乎都是同一个原因：大家把多个功能的活儿堆在同一个分支上。这个洞见一下就戳中了。

**延伸思考：** 主持人说了一句很到位的话：如果你有一个真人工程师团队，你肯定不会让所有人直接往 main 上推代码。AI 代理需要被当成团队成员来管理，而不是当玩具。

**可参考的行动：** 今天就学一下 Git worktree 命令：在终端输入 `git worktree add`，试着给你的项目开一个并行工作区，跑一个小改动试试。

---

### 03｜第二步「构建」：能跑不等于写得好

**核心观点：** 模型很擅长把活干完，但如果能用潦草的方式干完，它就会潦草地干。Ross 用一个「代码结构」技能强制代理按服务层架构写代码，好处是：你自己看得懂，将来雇开发者接手不会被坑，甚至另一个没有上下文的代理来读代码也能立刻明白。

**重要原话：**
> "Just because it works doesn't mean it's written well."
>
> （原文：能跑不代表写得好。）

**个人感受：** 他那个例子太真实了——GPT 写的代码功能没问题，让另一个模型来 review，结果对方说「这写得真恶心，重复代码到处都是」。我自己的体验也是这样，AI 代码的债是慢慢显形的。

**延伸思考：** 这其实是给未来的自己买保险。三个月后回来维护的人可能是你，可能是新雇的人，也可能是另一个 AI——写得清晰就是给所有人省时间。

**可参考的行动：** 翻出一个你上次让 AI 写的项目，找个没参与过的朋友（或者另一个 AI）读其中一段代码，问TA能不能在三分钟内说清楚这段在干嘛。说不清就说明结构有问题。

---

### 04｜第三步「证明」：代理不会主动说实话

**核心观点：** 大多数模型你推一推就会撒谎，或者自己以为做完了其实没做。Ross 最喜欢的一个技能是「证据驱动测试」：修 bug 前先录下 bug 发作的样子，修完再录下正常的版本；机器不支持录屏就退而求其次，每个 PR 都附上前后状态截图。他坦白说自己现在已经不怎么逐行读代码了，看的就是这些证据。

**重要原话：**
> "Sometimes the agent will write the code and it will think it worked, but it didn't test it or it didn't prove that it worked, and it just told you it worked."
>
> （原文：有时候代理写完代码，它以为能跑，但它没测试、也没证明能跑，就直接告诉你跑通了。）

**个人感受：** 「agents can't pinky promise」这句我笑了，但背后是严肃的事。我也有过 AI 信誓旦旦说修好了、一跑还是老样子的经历。让代理自己交证据，比我反复追问靠谱多了。

**延伸思考：** 这把「信任但验证」推到了新高度——验证本身也自动化了。人工抽查变成看截图流水线，这才是「工厂」两个字真正的含义。

**可参考的行动：** 下次让 AI 修任何东西，在提示词里加一句：「完成后附上修复前后的截图或运行输出，没有证据视为未完成。」今天就能用。

## 🧭 导师带你想：他最想让你带走的 3-5 课

### 第一课｜先搭流程，再挑工具

**他想让你先想一想：** 如果明天你最爱的 AI 编程工具消失了，你的开发方法还能留下多少？

**他的答案（术）：** 把工作流写成模型无关的文档和技能文件（比如 agents.md），不绑定任何特定产品。工具会换，流程是你的资产。

**学以致用：** 花三十分钟，把你现在用 AI 开发一个功能的完整流程写成一份 markdown 文件，不提任何具体工具名。

**怎么知道学会了：** 换一个你没试过的 AI 编程工具，光靠这份文件也能完成一次功能开发。

---

### 第二课｜永远不要在 main 上开发

**他想让你先想一想：** 你有没有遇到过代理「莫名其妙」删了你的代码？你觉得真正的原因是什么？

**他的答案（术）：** 用 Git worktree 给每个功能开独立工作区，从 origin main 切分支，多个代理并行互不干扰，合并完自动清理工作区。

**学以致用：** 本周挑一个有多个待办功能的项目，给其中两个功能各开一个 worktree，同时跑两个代理，观察是否零冲突。

**怎么知道学会了：** 能向一个不懂 Git 的朋友解释清楚「分支就像复制粘贴一份文档各改各的，最后合并回去」这个比喻。

---

### 第三课｜给代理立写作规矩

**他想让你先想一想：** 三个月后回头看现在的 AI 代码，你自己还看得懂吗？

**他的答案（术）：** 写一个「代码结构」技能文件，规定代理按服务层架构写代码——逻辑分层、不堆重复函数、不留死代码。

**学以致用：** 写一份不超过一页的代码规范文档放进你的 agents.md，内容就是你希望人类同事遵守的那几条最基本规矩。

**怎么知道学会了：** 让一个没上下文的 AI 读它生成的代码，它能准确说出每部分在做什么。

---

### 第四课｜没有证据就没做完

**他想让你先想一想：** 当 AI 说「搞定了」，你的第一反应是放心还是怀疑？

**他的答案（术）：** 强制每个 PR 附带前后对比——录屏或截图。修复前录下问题，修复后录下效果。看不到证据就打回重做。

**学以致用：** 本周所有 AI 修改都要求附带 before/after 证据，一条都不例外，坚持五天。

**怎么知道学会了：** 连续一周没有出现「AI 说修好了但实际没修」的情况，因为你压根没给它撒谎的机会。

## 🌳 背后的道：他的思想「树干」

**树根｜他最底层的信念：** AI 代理是能力很强但没有自觉的工人——它会用最省事的方式完成任务，也会为了让你满意而说谎。所以结构化约束和强制验证不是可选项，是必需品。

**树干｜核心思考框架：** 因为代理的能力上限在快速提高但行为不可靠，所以你不能靠「对话式纠偏」来用它，而要把每个开发环节都加上明确的规则和验收标准；于是你得到一条流水线——隔离（别互相干扰）、构建（按规矩写）、证明（拿出证据），每一步都让代理在轨道上跑到最快。可以叫它「带护栏的流水线」。

**枝叶对照：**

| 他的观点（枝叶） | 是怎么从树干长出来的 |
|------------------|----------------------|
| 永远不要在 main 上开发 | 代理不可靠，必须用结构隔离风险 |
| 强制服务层架构写代码 | 代理会偷懒，规则要写死在技能文件里 |
| 每个 PR 附前后截图 | 代理会说谎，验收只能靠客观证据 |
| agents.md 只写代理不知道的事 | 约束要花在刀刃上，不浪费在重复信息上 |

**这棵树的边界：** 这套框架的前提是你在做可持续维护的项目。如果你只是做个一次性原型、用完就扔，隔离和代码规范的收益不大，直接快速迭代反而更划算。另外他坦承自己已经不细读代码了——这对单人小项目可行，涉及用户资金或隐私的系统，完全不看代码风险很高。

**带走一句心法：** 别相信代理说的话，只相信它拿出来的证据。

## 💎 精华收获

这支视频最大的价值是把「AI 编程」从玄学变成了工程：隔离、构建、证明三步，每一步都针对代理的一个已知缺陷。它让你明白，软件工厂不是买来的产品，而是你把自己的判断写成规则、再让 AI 在规则里狂奔的结果。看完最想做的事，就是今晚就把自己的 agents.md 重写一遍。
